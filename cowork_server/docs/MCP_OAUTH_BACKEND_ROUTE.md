# MCP OAuth bridge — the backend routes we need (§10)

The agent side is built and tested (`agent/src/cowork_agent/oauth_bridge.py`,
`agent/tests/test_oauth_bridge.py`). It talks to three backend surfaces. **None
of them exists today.** This document is the contract; implement it and the
client needs no change.

## What `api_server` has today (verified, 2026-08-13)

- **GitHub device flow only.** `routers/github.py` + `github_oauth.py`:
  `POST /v1/user/github/connect/init` starts a GitHub *device* flow,
  `POST /v1/user/github/connect/poll` finishes it, `GET /v1/user/github/status`,
  `DELETE /v1/user/github/disconnect`. A device flow has **no redirect**, so
  there is no callback route to reuse.
- **Two token vaults exist. Use the server-encrypted one.**
  - `user_github_tokens` (migration `20260521_user_github_tokens.sql`):
    **server**-encrypted with Fernet (`github_oauth.encrypt_token`, key derived
    from `SUPABASE_SERVICE_KEY`), RLS denies all user access, a redacted
    `user_github_token_status` view is what the app reads. This is the table
    shape the MCP flow should copy.
  - `service_credentials` (migration `20260316_service_credentials.sql`):
    **client**-encrypted (the chat AES-256-GCM key) for cross-device sync. The
    server cannot read it, so it cannot act with it. Not usable here.
- **Caveat, and it is the opposite of §10:** `github.fetch_user_token()` exists to
  decrypt the token and **inject it into an E2B sandbox as `GITHUB_TOKEN`** (the
  migration's own comment says so). That is a raw secret inside a sandbox — the
  thing §10 rules out. Do not extend that pattern to MCP: the new routes should
  keep the token server-side, or hand out a short-lived scoped token (last
  section).
- **Pending-flow state is already stateless-by-design.** `register_pending` /
  `pop_pending` encode the whole pending flow into a Fernet ciphertext used as
  the `state` token, because the API server runs multiple replicas and an
  in-memory dict broke across them (the comment above it says so). **Do the same
  here** — see "Correlation" below.
- `grep -rn "oauth" main.py routers/` finds nothing else. There is **no**
  `/oauth/callback/{server}`, no generic OAuth start, no MCP-specific route.

## The flow

```
 phone/app          backend (api.chuk.chat)        provider          sandbox agent
     |                        |                       |                    |
     |                        |<---- 1. POST /v1/oauth/mcp/start ----------|
     |                        |----- {state, authorize_url} ------------->|
     |<-- 2. authorize_url ---|  (via the agent's notify channel)          |
     |                        |                       |     3. long-poll   |
     |--- 4. user authorizes in a normal browser ---->|     /pending/{state}
     |                        |<-- 5. GET /oauth/callback/{server}?code&state
     |                        |     constant-time state compare            |
     |                        |----- 6. {code} (one single read) --------->|
```

The sandbox needs **no inbound port and no tunnel**: it only ever makes outbound
calls to our own backend.

## 1. `POST /v1/oauth/mcp/start`

Auth: `Authorization: Bearer <supabase access token>` (same as
`/v1/tools/brave/search`).

Request:

```json
{
  "server": "linear",                    // required, a name in the server-side registry
  "scopes": ["read", "write"],           // optional, narrowed against the registry
  "code_challenge": "<base64url S256>",  // required, PKCE, generated by the agent
  "code_challenge_method": "S256"        // required, only S256 is accepted
}
```

**The request carries a name, nothing else.** Which provider that name means —
authorize endpoint, token endpoint, client id, allowed scopes — comes from a
**server-side registry**. Do **not** accept an `authorize_endpoint`, a
`client_id`, or a `redirect_uri` from the client: a sandbox that could name its
own authorize endpoint could make `api.chuk.chat` hand the user a
trustworthy-looking link to a credential-phishing page. An unknown name is a
`400`. If custom providers are ever needed, they get their own registration flow
with origin validation and an explicit user confirmation in the app — not a field
on this route.

**PKCE ownership: the agent owns the verifier.** It generates
`(verifier, challenge)` (`oauth_bridge.pkce_pair`, S256), sends only the
challenge here, and sends the verifier only to the provider's token endpoint. So
the backend never holds the verifier and never has to hand a secret *back* into
the sandbox — and a stolen `code` is useless without it. The backend's job is to
put `code_challenge` / `code_challenge_method=S256` into the authorize URL and to
reject a `start` that has no challenge.

Response `200`:

```json
{
  "state": "<opaque, >=32 bytes of entropy, URL-safe>",
  "authorize_url": "https://provider/authorize?response_type=code&client_id=…&redirect_uri=https%3A%2F%2Fapi.chuk.chat%2Foauth%2Fcallback%2Flinear&state=…&scope=…&code_challenge=…&code_challenge_method=S256",
  "expires_in": 600
}
```

Errors: `400` unknown/unconfigured server, `401`/`403` token, `429` rate limit,
`503` no OAuth configuration for that provider. Body `{"error": "<text>"}` — the
client already reads that shape.

`redirect_uri` **must** be `https://api.chuk.chat/oauth/callback/{server}` and
must be registered with the provider. Never a localhost port.

## 2. `GET /oauth/callback/{server}`

The provider's redirect target. **Public, no auth** (a browser arrives here
without our bearer token). Query: `code`, `state`, optionally `error`,
`error_description`.

Behaviour:

1. Decode `state` and correlate it to the pending flow (below). Compare with
   **`hmac.compare_digest`**, never `==`.
2. On mismatch, expiry, or an already-consumed flow: return a plain HTML page
   saying the link is no longer valid, HTTP `400`. **Do not** echo `state` or
   `code` back into the page.
3. On success: store the `code` against the flow with a short TTL (60 s is
   enough; the agent is already polling) and a `consumed=false` marker, then
   render a "you can close this tab" page.

If `error` is present, store a **bounded, allow-listed error code** (the RFC 6749
set: `access_denied`, `invalid_scope`, …; anything else becomes
`provider_error`) as the flow's failure, and render a **static** failure page.
Never render `error` or `error_description`: they are attacker-controllable query
parameters, and echoing them puts arbitrary text — or HTML — on the
`api.chuk.chat` origin. The stored code is what `/pending/{state}` returns; it is
short and machine-readable, which is all the agent needs.

## 3. `GET /v1/oauth/mcp/pending/{state}`

Auth: the account bearer token. Query: `wait` (seconds, 0–30) enables long-poll.

Responses:

- `200 {"state": "…", "code": "…"}` — exactly **once**. Mark the flow consumed in
  the same transaction that reads it.
- `204` — still pending (the client keeps polling within its own budget).
- `404` — unknown state.
- `410` — expired, already consumed, or failed. Optional `{"error": "access_denied"}`
  for a provider-side failure.

The flow is bound to the account that started it: a `state` presented by another
user is a `404`, exactly like `pop_pending` does for GitHub today.

## Correlation and storage

Follow `github_oauth.register_pending`: **encode the flow into the `state`
token** with Fernet (`{"u": user_id, "s": server, "n": nonce, "e": expiry}`), so
any replica can decode it with no shared store. The `code` itself does need
short-lived shared storage between the callback replica and the polling replica —
one Supabase row (`mcp_oauth_pending`: `state_hash`, `user_id`, `server`,
`code_encrypted`, `consumed`, `expires_at`) or Redis with a 60 s TTL. Key it by
the **hash** of the state, never the state itself, and store the code
**encrypted** with the existing Fernet cipher.

Cleanup: delete rows past `expires_at` on a schedule; the row is worthless once
consumed.

## Security requirements (all of these are load-bearing)

- **Constant-time state compare** (`hmac.compare_digest`).
- **Single use**: the read that returns the code marks it consumed atomically.
- **Short TTL**: 10 minutes for the flow, ≤60 s for a delivered code.
- **PKCE (S256), verifier owned by the agent.** The backend stores the
  *challenge* with the flow (or simply passes it into the authorize URL) and
  never sees the verifier. Reject a `start` without a challenge, and reject any
  method other than `S256`.
- **A registry-only provider lookup** (see above). No client-supplied endpoints.
- **No secret in the redirect page**, no `code` in logs, no `state` in logs.
- **Rate limit** `start` per account: an agent in a loop must not be able to open
  thousands of flows.

## Optional, and preferable: exchange in the backend

The client currently exchanges the `code` for a token itself
(`oauth_bridge.http_token_exchange`), which is the one place a third-party token
lives in the sandbox — documented and bounded in
`agent/src/cowork_agent/oauth_bridge.py` (memory only, redacted `repr`, never
journaled, dies with the process).

If the backend does the exchange and stores the token in the vault, the sandbox
can hold a **short-lived, scoped** access token instead, or none at all for
servers we proxy. That would need one more route:

```
POST /v1/oauth/mcp/token   {"server": "linear"}  ->  200 {"access_token": "…", "expires_in": 3600}
```

The agent-side change is then one function: replace `http_token_exchange` with a
call to that route. Everything else — the state compare, the single use, the
Event-gated wait — stays as built. Note that in **that** design the backend does
the token request, so the backend must own the PKCE verifier: it would generate
the pair itself and the `code_challenge` field on `start` disappears. The two
designs are mutually exclusive, which is exactly why "who owns the verifier" is
answered explicitly in both.
