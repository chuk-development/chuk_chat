# Audit 2026-07-29 — open findings

Six parallel audits ran over the chat send/streaming paths, tool handlers,
storage/sync/offline, message rendering, and auth/encryption. What was fixed
in `71a95f5`, `dae2104` and `6027685` is not repeated here. **This file is the
backlog of what is confirmed and still broken.**

Findings are grouped by whether acting on them is safe without a way to
reproduce first.

---

## A. Data-loss and cross-account bugs — fix next, but each needs a repro

### A1. Offline send of a *new* chat loses the message entirely — CRITICAL
`saveChat` has no local-only write path: `chat_storage_crud.dart:1028` inserts
into Supabase and only writes the SQLite cache after that succeeds. Offline it
throws, and `chat_persistence_handler.dart:140-148` swallows it ("chats will
sync when back online" — nothing will, nothing was written).

The queue row survives, so on reconnect `OfflineSendExecutor._execute` does
`loadFullChat(...)` → `null` → `'chat not loaded'` → `ExponentialBackoff`
treats an unknown error as retryable (`exponential_backoff.dart:218`) → retried
on every connectivity edge, forever, never delivered.

**Repro:** airplane mode → new chat → send → kill app → relaunch.

### A2. Sync deletes locally-created chats mid-save — CRITICAL
`chat_sync_service.dart:250` snapshots cloud ids, then after several awaits
removes every local id missing from that snapshot (`:273`, `:332-334`). Unlike
the merge path (`chat_storage_sync.dart:286-301`), the delete path checks
neither `savingChats` nor `pendingSaves`. A chat inserted during that window is
wiped from memory and cache and marked deleted for 2 minutes
(`chat_storage_state.dart:108`), so every later persist of the streaming answer
is dropped by `chat_persistence_handler.dart:95-101`.

Same unguarded removal in the title sync, `chat_storage_sidebar.dart:343-349`,
without `markDeleted` — there the next persist calls `saveChat` on an existing
PK → duplicate-key → swallowed → turn lost. And `chat_storage_sidebar.dart:220-228`
wipes the whole sidebar (and the title cache) on a transient empty result set.

### A3. Last-write-wins destroys the other device's turns — CRITICAL
`_doUpdateChat` (`chat_storage_crud.dart:1161-1170`) replaces the entire message
array with no version column and no `updated_at` guard, and **no chat UI
subscribes to `ChatStorageService.changes` for the open conversation** — so a
synced update never refreshes `_messages`. Two devices with the same chat open:
the one that sends last overwrites the other's turns on the server and in both
caches, silently.

Secondary, same statement: `'image_paths': imagePaths.isNotEmpty ? … : null`
nulls the cleanup list on any update whose messages carry no `.enc` paths →
images orphaned in storage forever.

### A4. Mobile's anti-kill snapshot never writes the streaming message — HIGH
`updateBackgroundChatMessage` addresses the target by array index
(`chat_persistence_handler.dart:281-283`), but the `Thinking...` placeholder is
filtered out of every write (`:52`, `chat_storage_crud.dart:858`). At tick time
`placeholderIndex >= messages.length` is always true, so every tick returns
early — and so does `_markAssistantMessageInterrupted`, meaning the
`interrupted` flag never reaches storage and Continue is not offered after an
OS kill. Address by `messageId` (the field already exists on `ChatMessage`),
not by index — the index is resolved against a *reloaded* list and can write
onto the wrong message.

### A5. Offline queue is not user-scoped and is never cleared on sign-out — HIGH
`pending_messages` has no `user_id` (`offline_queue_service_native.dart:72-81`)
and `listAll()` returns everything. Sign-out does not touch it. User A composes
offline, signs out, user B signs in → the queue drains with **B's token** and
**A's prompt**, billed to B. No attempt cap, no dead-letter.

### A6. `kv_cache` is keyed globally — workspaces leak across accounts — HIGH
`local_chat_cache_native.dart:77-82` — `kv_cache(key PRIMARY KEY, value)`, no
`user_id`, unlike `chat_cache` which correctly uses `(user_id, id)`.
`WorkspaceStorageService._cacheKey = 'cached_projects'`. User A's project names
render in user B's sidebar until the network load replaces them.

### A7. Offline sign-out leaves the AES key and plaintext chats in memory — HIGH
`SessionManagerService._performLogoutCleanup:167-177` skips the whole cleanup
when offline. `chat_ui_mobile.dart:1209` signs out via `SupabaseService.signOut()`
directly, bypassing `AuthService` (no `clearKey`, no `MultiplexSession.shutdown`).
On the next sign-in `loadSavedChatsForSidebar` short-circuits on
`if (ChatStorageState.cacheLoaded) return;` — user B sees user A's chat titles.

Also never cleared on sign-out: `ImageStorageService._imageCache` (up to 50 MB
of *decrypted* image bytes — `clearCache()` has zero callers),
`PdfAttachmentService._cache` (same), `ArtifactStorageService._cacheByChatId`
and `activeArtifactNotifier`.

### A8. `ChatPreloadService.reset()` is dead code — MEDIUM
No callers. After a user switch `startBackgroundPreload` returns immediately
("already complete"), so B's chats are never hydrated and `exportChats`
silently exports only what happens to be loaded.

## B. Encryption — do not touch without a reproduction harness

These are the highest-severity findings in the audit and also the ones where a
wrong "fix" destroys user data irreversibly. **Nothing here was changed.**
Recommended order: build a test harness that can round-trip a key rotation
against a scratch account first.

### B1. `initializeForPassword` writes the payload version into the key-version slot
`encryption_service.dart:317` writes `_payloadVersion` ('1') into
`chat_key_version_<uid>`. The service's own comment at `:458-460` says that slot
holds the *key* version. `_syncMetadataInBackground` then makes the local value
authoritative (`:462-464`) and PATCHes the server back to 1.

Consequence: after any password reset, signing in with the password downgrades
the account's key version. New chats are then sealed with the v2 key and tagged
`kv:1`; two different keys claim version 1. The next reset hits
`promoteCurrentToPrevious` → `previousKeys.any((k) => k.version == 1)` → returns
null → `set_new_password_page.dart:89-91` throws *after* the Supabase password
was already changed at `:70`. The v2 salt is never preserved and everything
written under it becomes unrecoverable.

This is independent of the already-known `rotateKeyForPasswordChange` tearing.

### B2. A stale device can overwrite the remote salt of a freshly rotated key
`encryption_service.dart:450-455` — local salt always wins, no recency check,
fired unawaited from `tryLoadKey` on every start. Device B (still on the old
salt, its revision-mismatch logout deliberately delayed by 12 s,
`session_manager_service.dart:121-122`) PATCHes `chat_kdf_salt` back to the old
value, destroying the only server-side copy of the new key's salt.

### B3. Password change re-encrypts only `encrypted_payload`
`chat_storage_mutations.dart:144-151`. Not migrated, all sealed with the same
key: chat titles, images, PDF attachments, artifacts, workspace files, per-model
prompts, user skills, notes/identity, and **third-party service credentials**.
After a password change every image and PDF fails to decrypt forever and every
connected service silently reports "not connected".

### B4. Failed migration leaves the DB half-sealed with a discarded key
`encryption_service.dart:538-551` — chat-by-chat writes, no journal, no
transaction. The rollback's first statement is
`if (user == null) return;` (`chat_storage_mutations.dart:135-136`), so if the
session dropped mid-migration the rollback silently does nothing. A password
*change* never records a `previous_keys` entry, so there is no recovery path.

### B5. Sidebar wipes chat titles when title decryption fails, and caches the wipe
`chat_storage_sidebar.dart:435-440` swallows, `:303-315` stores the null-title
chat, `:362-365` writes it to the cache. After B3 this blanks the entire
sidebar — indistinguishable from losing all history.

### B6. `_decryptMap` drops undecryptable entries, then persists the truncated map
`per_model_system_prompt_service.dart:355-365` skips entries that fail to
decrypt; `_persistAll` (`:386`) and `_saveRemote` (`:493`) then write that map
back over both stores. The other prompts' ciphertext is deleted — recovering
the key later cannot bring them back.

### B7. Recovery aborts the whole batch on one mis-tagged row
`password_reset_service.dart:114-141` selects rows by `kv` tag but probes the
password against an arbitrary `rows.first`. One mis-tagged row makes the
*correct* password report "Wrong password", and chats tagged with a version that
has no `previous_keys` entry are never offered for recovery at all.

### B8. `_runExclusive` has no owner tracking — re-entrancy deadlocks the service
`encryption_service.dart:823-836`. `rotateKeyForPasswordChange` runs its
callback inside the lock; that callback's `encrypt` → `_ensureKey` →
`tryLoadKey` → `_runExclusive` chains onto a lock that cannot resolve. Every
later encrypt/decrypt hangs until the app is killed.

### B9. The raw AES key is in SharedPreferences on macOS and on Linux without the keyring flag
`encryption_service.dart:216-241`. Any process running as the user can read the
key and decrypt the whole history without the password. Worth an explicit,
documented decision rather than an inherited fallback.

## C. Remaining mobile/desktop divergence

`ChatHistoryBuilder` removed three copies of the history builder. These are
what is left, in the order they are worth doing.

### C1. Mobile ignores workspace custom system prompts — CONFIRMED user-visible
`chat_ui_desktop.dart:1129-1140` replaces the base prompt when a workspace has
`hasCustomPrompt`. Mobile has no such branch — `_resolveWorkspaceForCurrentChat`
exists only in `chat_ui_desktop.dart:1115`. Same account, same chat, different
persona depending on the device. `_resolveSystemPromptForSend` is otherwise
byte-identical between `chat_ui_desktop.dart:1126-1207` and
`chat_ui_mobile.dart:2469-2536` and should become one service.

### C2. Mobile ignores "memory disabled" workspaces
Both desktop `createSession` calls pass
`skipIdentity: assistant != null && !assistant.memoryEnabled`; mobile's two
omit it. In a workspace with memory off, mobile still exposes the `notes` tool
and injects identity/memory — it writes notes the user opted out of. Blocked on
C1 (needs the workspace resolver moved out of the desktop widget).

### C3. Mobile's token budget is image-blind
`chat_ui_mobile.dart:2442-2466` is a fourth, sync, image-less history variant
fed to `prepareMessage`. `TokenEstimator` charges 1000 tokens per image block,
so with 8 images in scrollback mobile under-estimates by ~8000 tokens, never
shows the "too much context" guard, and asks for a `maxResponseTokens` that
does not fit. Fix: build the history once with `ChatHistoryBuilder` before the
user bubble is appended and pass the same list to both.

### C4. The tool loop exists three times
`streaming_message_handler.dart:479-1149` (hardened) versus
`desktop_send_logic.dart:1548-2075` and `:441-873`. Missing from **both**
desktop copies: the 20-pass ceiling, pass-level reconnect with backoff,
`cache_miss` replay, error salvage, `finalizeStaleToolState`, the
Continue-generation hook, `existingBlocks` idempotency, interleaved
text↔tool ordering, the final-pass reasoning block, and
`dedupeFinalTextAgainstBlocks`.

Do this as a **deletion**: make `chat_ui_desktop` drive `StreamingMessageHandler`
and remove both desktop copies. Extracting a shared helper from three drifted
copies only creates a fourth place to drift.

Note `accumulatedText` on desktop is never written — only cleared and read — so
the "prepend accumulated text" comments there are no-ops today. Anything that
fixes desktop's multi-pass text loss has to make that live first.

### C5. Desktop resend has no offline handling
`NetworkStatusService`, `_enqueueOfflineSend` and `isMessageOperationInProgress`
appear only inside `_sendMessage`. `_submitEditedMessage` has none, so an
edit/resend during a network blip destroys the turn where the composer would
have queued it. It also never sets `isMessageOperationInProgress`, so
`didUpdateWidget` can swap the chat out from under an in-flight resend.

### C6. Smaller pairs
Verbatim duplicates worth collapsing: `_resendMessageAt`, the `ask_user`
callback, `_editMessageAt` / `_cancelEditMessage`, `_processToolImages` (mobile
runs it before final block assembly, desktop after), `_cancelPendingMessage` /
`_drainPendingMessage`, the artifact-rollback preamble in both
`_submitEditedMessage`s, and the debug-payload merge (mobile discards the
payload when the chat is not active; desktop persists it).

## D. Rendering

- **D1.** The content-blocks path never reads `widget.reasoning`
  (`message_bubble.dart:1028-1300`, gate at `:820`, `:2460`), so live reasoning
  for the current pass is invisible.
- **D2.** The bubble's dedup (`message_bubble.dart:1060-1112`, two cases, built
  from *unstripped* text) disagrees with the handler's
  (`dedupeFinalTextAgainstBlocks`, four cases, stripped) → the whole answer can
  render twice.
- **D3.** `stripArtifactTagsForDisplay` (`artifact_tag_parser.dart:142-147`)
  truncates from the first `<artifact` with **no code-span exclusion** — unlike
  the tool-protocol strip. Explaining the tag in prose loses the rest of the
  message.
- **D4.** `isDuplicateOfEarlierTextBlock` uses substring containment
  (`round_content_block_service.dart:287`) → a short later block ("Yes.", "42")
  that appears inside an earlier one is dropped from the transcript.
- **D5.** Tool-bar header shows green "done" while the expanded cards show
  orange/blue "running" for a finalized message with stale calls
  (`message_bubble.dart:2249-2325` vs `:2489-2513`).
- **D6.** `_hasModelInfo` is not gated on `!isContentBlock`
  (`message_bubble.dart:2469`) → the model-info card repeats once per round.
- **D7.** Mid-stream `<chart>{…` renders as raw JSON: `_hasVisualBlocks` matches
  the opening tag, `_buildVisualContent` requires the closing one
  (`:1303-1305` vs `:309`). And `:1417` prints the `FormatException` — including
  a fragment of the payload — into the chat.
- **D8.** Desktop never passes `onContinueGeneration`; `initialEditText`,
  `onSubmitEdit`, `onCancelEdit` and `onRetryToolPass`/`canRetryToolPass` are
  dead on both platforms. `isReasoningStreaming` means different things per
  platform, so desktop never shows "Processing prompt..." and renders
  Retry/PDF under a live message.
- **D9.** Per-frame cost in `build()`: `_extractSources` recompiles two regexes
  and rescans every tool result (`:2786-2795`), `ImageMeta.decode` is the one
  payload without a decode cache, `MarkdownMessage`'s cache ignores font-size
  changes, and the content-block child list has no keys.
- **D10.** ~70 hardcoded English strings in the chat render path bypass
  `lib/l10n/strings_en.dart` (full list in the audit transcript; includes
  'Continue generation', 'Reasoning', 'Args: ', 'Running…', the sources
  pluralisation, and every label in `message_actions_handler.dart`).

## E. Tool handlers

- **E1.** ~100 failure paths were mislabelled as success; fixed centrally in
  `71a95f5` by broadening the detection. **The real fix is still open:**
  handlers should return `({String output, bool isError})` so the failure is
  stated rather than sniffed. String sniffing also causes the inverse bug —
  `whoop_tools.dart:121`/`:138` return raw upstream bodies that can begin with
  "Error". Only `sandbox_read` was opted out.
- **E2.** Missing timeouts remain on every Spotify call
  (`platform_tools_native.dart:254-276`) and in all of `nextcloud_service.dart`
  (zero `.timeout(` in the file). The three map lookups were fixed.
- **E3.** Exceptions escape the handler entirely where the auth/arg parsing sits
  *before* the `try`: `whoop_tools.dart:18,26,28`,
  `platform_tools_native.dart:114-142`, `:702` (no try/catch at all),
  `typst_tools.dart:148`.
- **E4.** Uncapped results feed the context: `nextcloud_tools.dart:45` (whole
  remote file), `whoop_tools.dart:121/128/138`, `typst_tools.dart:261-263`,
  `crypto_tools.dart:113-230` (~1000 lines), `weather_tools.dart:227`,
  `platform_tools_native.dart:282`. `sandbox_tools.dart:14-24` and
  `web_tools.dart:12-14` show the pattern to copy.
- **E5.** `whoop_tools.dart:103-108` puts the access token in the query string,
  where it lands in access and proxy logs. Use a header.
- **E6.** `nextcloud_service.dart:35` stores a user-supplied `serverUrl` with no
  scheme validation and builds Basic-auth requests from it — an `http://` entry
  sends credentials in cleartext.
- **E7.** Eight copies of the mux → HTTP-fallback → status-check → decode block,
  each with its own timeout (25/30/45/60/120 s) and its own error wording. This
  is *why* the error prefix drifted. One `callServerTool(...)` helper would fix
  ~35 of the mislabelled sites at the source. Also duplicated:
  `_tryDecodeJsonObject` ×3, `_coerceInt` ×4 (one incompatible),
  `_coerceDouble` ×2, the auth-gate + switch skeleton ×9.

## F. Test coverage that does not exist

No tests at all for: `multiplex_connection`, `multiplex_session`,
`websocket_chat_service`, `StreamingMessageHandler`, `desktop_send_logic`, the
reconnect/retry classifier, `_continueGenerationAt`, the composer
(`_buildSearchBar`), or `ToolEnforcer.checkForHallucination`. There is no
`integration_test/` directory.

The cross-model tool-call conformance harness discussed earlier is still not
built: capture raw streams per model × provider into fixtures, then replay them
through the Dart parser in `flutter test`. The client cannot currently export a
raw assistant stream at all — `DebugChatFormatter` prints only payload counts,
and the final pass's raw output is never recorded anywhere.
