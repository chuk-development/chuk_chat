# Skills: Catalog + Local Edit + Sync — Build Plan

Status: planned, not started. Owner decisions locked 2026-08-26.

Reworks the Agent Skills feature into a single model: **every skill is a
local, user-owned, editable record**, stored in SQLite and synced to Supabase.
We ship a **catalog** (hosted on GitHub) that acts as a *seed and update feed* —
not a read-only live layer. The user (and the AI) can edit any skill. When we
push a catalog update, pristine copies auto-update and edited copies get an
update *suggestion* the user can accept or ignore. Adds the missing **Level-3
(bundled files)** support so catalog skills can ship `scripts/`, `references/`
and `assets/` sub-folders.

`FEATURE_SKILLS` is removed — skills are always on.

## What exists today (verified)

- Two skill sources: **builtin** (`kBuiltinSkills`, compiled by
  `tool/gen_skills.dart` from `assets/skills/<name>/SKILL.md`) and **user**
  (`user_skills_service.dart`, E2E-encrypted rows in Supabase table
  `user_skills`, SharedPreferences ciphertext cache, cap `kMaxUserSkills = 20`).
- `SkillRegistry` (all static) merges them; clean seam
  `SkillRegistry.setUserSkills(List<Skill>)`. One strict parser for every
  source: `parseSkillMarkdown`.
- Progressive disclosure Levels 1 (name+desc always in prompt) and 2 (body on
  `skill` tool call) are built; **Level 3 is not**. The `Skill` model holds a
  single `body`, no file tree.
- The app already has a `bash` tool (`tool_registry.dart:814`), `run_command`
  (`:1492`) and `bash_sandbox.dart` — so a skill that references a command is
  executed by whatever tools the agent already has, not by any skill-specific
  code (see "Scripts" below).
- `FEATURE_SKILLS` gates: `tool_registry.dart:1581`, `tool_call_handler.dart:331`,
  `settings_page.dart:238`, and `platform_config.dart:118`. All get removed.

## The model

One record type. Every skill the user has is a row they own and can edit. The
row remembers where it came from and what the upstream version was, so updates
reconcile without clobbering edits.

### Skill record (SQLite `skills`, synced to Supabase, body E2E-encrypted)

- `id` — stable uuid.
- Parsed fields (the user's *current* version): `name`, `description`, `body`,
  `license`, `compatibility`, `metadata`, `allowed_tools`.
- `origin` — `catalog` (seeded from our GitHub catalog) or `user` (created from
  scratch by the user or the AI).
- `catalog_name` — for `origin = catalog`, the catalog skill this tracks
  (matching key for updates). Null for user-created.
- `baseline_hash` — hash of the body as last taken from the catalog. Null for
  user-created. **This is how we detect edits:**
  `edited = sha256(current_body) != baseline_hash`.
- `baseline_body` — the last catalog body text, kept for the diff shown in an
  update suggestion. (Small; optional but makes the suggestion UI real.)
- `updated_at`, `user_id`.

The agent still only ever sees `name` + `description` (Level 1) until it
activates a skill. `origin`/`baseline_*` are storage bookkeeping, never in the
prompt.

## Catalog (GitHub repo, seed + update feed)

New repo, e.g. `chuk-development/chuk-skills`, branch `main`:

```
skills-repo/
  index.json                     # manifest — client fetches this first
  skills/
    browser-skill/
      SKILL.md
      references/REFERENCE.md
      scripts/extract.py
      assets/template.json
    another-skill/
      SKILL.md
```

`index.json`:

```json
{
  "version": 1,
  "generated_at": "2026-08-26T00:00:00Z",
  "skills": [
    {
      "name": "browser-skill",
      "description": "Drive a headless browser. Use when a task needs a real page render.",
      "path": "skills/browser-skill",
      "hash": "sha256:...",              // over SKILL.md; the update trigger
      "license": "Apache-2.0",
      "allowed_tools": ["bash"],
      "resources": ["references/REFERENCE.md", "scripts/extract.py", "assets/template.json"]
    }
  ]
}
```

`index.json` carries `name` + `description` + `hash` for every skill, so a
refresh needs only the manifest to decide what changed. Bodies and resources are
fetched lazily. Generated by a script in the repo (never hand-edited).

Raw base is a const, dart-define overridable:
`kSkillsCatalogBase = https://raw.githubusercontent.com/chuk-development/chuk-skills/main/`.
- Manifest = base + `index.json`
- Body     = base + `<path>/SKILL.md`
- Resource = base + `<path>/<relPath>`

## Reconciliation (on startup + manual refresh)

The heart of the feature. For each skill in the fetched manifest:

```
local = skills.where(origin == catalog && catalog_name == cat.name).first
if local == null:
    # user doesn't have it -> add automatically
    body = fetchBody(cat)
    insert(origin: catalog, catalog_name: cat.name,
           body: body, baseline_hash: cat.hash, baseline_body: body, ...parsed)
else if sha256(local.body) == local.baseline_hash:
    # pristine (user never edited) -> silent auto-update
    if cat.hash != local.baseline_hash:
        body = fetchBody(cat)
        local.body = body; local.baseline_hash = cat.hash; local.baseline_body = body
else:
    # user (or AI) edited it -> never clobber
    if cat.hash != local.baseline_hash:
        queueUpdateSuggestion(cat, local)   # UI shows diff: "take ours / keep mine"
```

- **Accept a suggestion** → `local.body = catalog body`, `baseline_hash`/
  `baseline_body` updated. **Ignore** → nothing changes; the same suggestion
  will not re-nag unless the catalog hash moves again (compare against the *new*
  cat.hash, not the old baseline).
- **Catalog removes a skill** → leave the user's copy untouched (it is theirs).
  Never auto-delete.
- A user-created skill (`origin = user`) is never touched by reconciliation.

Reconciliation runs on startup and on a manual "Check for updates" action.
Suggestions surface as a badge/count in Skills settings.

## Storage: SQLite primary + Supabase sync

Move the current Supabase-primary `user_skills` path to the chat-cache pattern:
SQLite is the local source of truth, Supabase mirrors for cross-device sync,
cache-first reads.

- Native: new SQLite table `skills` in `chat_cache.db` (bump `_dbVersion`, add an
  `onUpgrade` step). Columns per the record above; body stored encrypted.
- Web: SharedPreferences fallback via the existing `kv*` methods
  (`local_chat_cache_web.dart`), keyed per user.
- Supabase: extend table `user_skills` with `origin`, `catalog_name`,
  `baseline_hash`, `baseline_body` (baseline_body encrypted too). Document the
  table in `docs/DATABASE.md` (currently undocumented) and add a migration via
  the Management API query endpoint (never `supabase db push` — see memory).
- Keep E2E encryption on `body` and `baseline_body`.
- Drop the flat `kMaxUserSkills = 20` cap, or raise it — the catalog alone can
  exceed 20. Decide a sane ceiling (e.g. 200) to bound prompt Level-1 cost.

`Skill` model gains `origin`, `catalogName`, `baselineHash`, `baselineBody`, and
`resources` (see Level 3). Every write still routes through `parseSkillMarkdown`
so validation/trust stays uniform.

`SkillRegistry` collapses to a single layer fed from the local store
(`setSkills(List<Skill>)`); there is no separate builtin/remote/user precedence
anymore because everything is one owned list. The compiled `kBuiltinSkills` stay
only as the **first-run seed** when there is no local store and no network yet.

## Level 3: `read_skill_resource`

New builtin tool so the agent pulls `references/` / `scripts/` / `assets/` on
demand.
- Args `{ skill, path }`. Validates `path` is in the skill's `resources` and has
  no `..` traversal. Fetches from the catalog (by `catalog_name` → path) and
  caches by `catalog_name@hash/relPath`.
- Content is injected into the next prompt rebuild under
  `## ACTIVE SKILL RESOURCE: <skill>/<path>` (same trick the body uses to dodge
  the 4000-char tool-result truncation). The tool itself returns a short ack.
- User-created skills have no resources in v1.

## Scripts / command execution

No skill-specific execution path. A skill referencing a command (e.g. ffmpeg) is
run by whatever tools the agent already holds:
- If the skill's `allowed-tools` includes `bash`/`run_command` and that tool is
  enabled, the agent runs it.
- In the normal chat UI where bash is sandboxed/off, the agent says it can't —
  acceptable. The skill still works as description.
- When CoWork lands (bash runs freely on the user's laptop), the *same* skills
  execute unchanged. Nothing to wire now.

## Agent-authored skills: `write_skill`

New builtin tool. The AI can create or update a skill on the user's request or
autonomously when useful.
- Args `{ name, markdown }` (a full SKILL.md) or structured fields.
- Validates via `parseSkillMarkdown`. Create (new `origin = user`) or update an
  existing row (counts as an edit: body diverges from `baseline_hash`, so future
  catalog updates become suggestions, not silent overwrites).
- Autonomous edits are allowed but must be surfaced (a note in the turn + the
  Skills settings shows "edited by AeneasAI at <time>"), so the user can review
  and revert.
- Pair with `delete_skill` for symmetry (user-created only; a catalog skill is
  "reset to catalog version", not deleted).

Tool registration for both new tools follows the existing 4-spot pattern
(`tool_registry.dart` ×2, `tool_executor.dart`, `tool_call_handler.dart`
non-factual set) + an executor `case`.

## UI (Skills settings)

`skills_settings_page.dart`:
- One editable list. Each skill shows origin (Chuk catalog vs Yours), edited
  state, and an "Update available" badge when a suggestion is queued.
- Actions: edit (opens the markdown), reset-to-catalog (for catalog skills),
  delete (user-created), and per-suggestion take/keep with a diff view.
- Install: **paste SKILL.md text** or **pick a `.md` file** → new `origin = user`
  skill. (`file_picker` already a dependency — mind the win32 ceiling in memory.)
- A "Check for updates" button triggers reconciliation.

## Security

- Catalog is authored by us → trusted; `allowed-tools` auto-approval fine for
  catalog-origin skills while pristine.
- Once a skill is edited (by user or AI) or is user-created, treat
  `allowed-tools` as untrusted: do **not** auto-approve tools without an explicit
  confirm. 36.8% of publicly shared skills carry a flaw, 84% in the SKILL.md
  prose itself.
- `read_skill_resource` rejects any path not in the manifest `resources` and any
  `..`.

## Build order (milestones — one per session; green tests + CodeRabbit + commit)

- **M1 — Remove the flag + model/storage foundation**: delete `FEATURE_SKILLS`
  and its 4 gates; add `origin`/`catalogName`/`baselineHash`/`baselineBody`/
  `resources` to `Skill`; SQLite `skills` table + web fallback; migrate the
  Supabase `user_skills` columns. Tests + freshness test still green.
- **M2 — Registry single layer + store service**: collapse `SkillRegistry` to
  one owned list fed from SQLite; first-run seed from `kBuiltinSkills`; Supabase
  sync (cache-first). Tests.
- **M3 — Catalog fetch + reconciliation**: `SkillsCatalogService` (manifest
  fetch, TTL cache, lazy body). The reconciliation algorithm with the
  baseline-hash logic. Tests for all four branches (add / auto-update / suggest /
  user-created-untouched).
- **M4 — Level-3 `read_skill_resource`**: registration, lazy resource fetch,
  prompt-rebuild injection, scripts-as-text. Tests.
- **M5 — `write_skill` (+ `delete_skill`)**: agent authoring, autonomous-edit
  surfacing. Tests.
- **M6 — UI**: editable list, origin/edited badges, update suggestions + diff,
  paste/`.md` install, check-for-updates.
- **M7 — The repo + docs**: create `chuk-development/chuk-skills`, `index.json`
  generator, seed skills (mirror the current builtins). Update `CLAUDE.md`,
  `docs/DATABASE.md`; remove stale `FEATURE_SKILLS` references from `run.sh`
  etc.
